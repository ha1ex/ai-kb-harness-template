# Обновлять проекты без потери своего контекста

## Главное

`kb:update` сравнивает исходную версию оснастки, текущие файлы проекта и выбранный выпуск шаблона. Контент и настройки проекта сохраняются. Если один файл изменён и локально, и в шаблоне, инструмент показывает конфликт.

Сначала посмотрите изменения, затем примените их к чистой рабочей копии, проверьте результат и создайте коммит. Восстановление предыдущего состояния остаётся обычной Git-операцией над вашим коммитом обновления.

## Версии и исходная база

- `.template-manifest.json`: `schemaVersion: 2` задаёт формат манифеста, `templateVersion` — версию оснастки.
- `.template-baseline.json`: исходные хеши распространяемого шаблона; создаётся автором выпуска и используется при первой инициализации.
- `.harness/lock.json`: установленная база конкретного проекта, отдельные хеши файлов и значения управляемых JSON-полей. Коммитится вместе с проектом.
- `package.json`: версия исходного репозитория шаблона совпадает с выпуском. Версия вашего приложения принадлежит вам и updater её не меняет.
- Версии отдельных документов и схем данных не зависят от версии harness.

Выпуски получают числовые теги вида `v0.4.0` и CHANGELOG. До 1.0 изменение форматов объявляется в minor-релизе с инструкцией миграции; patch содержит совместимые исправления. После 1.0 несовместимый контракт требует следующего major.

Начальная база содержит неизменяемое имя выпуска и хеши. Точный upstream-коммит записывается после разрешения версии через Git при обновлении или явном принятии базы. Он не выдумывается из HEAD нового проекта: GitHub создаёт для него независимую историю. Включить хеш коммита в тот же самый коммит также нельзя без самоссылки.

## Обычное обновление

```bash
pnpm kb:update --ref v0.4.0
pnpm kb:update --ref v0.4.0 --apply
pnpm run setup
pnpm test
pnpm check
pnpm viewer:build
```

Подставьте выпуск, на который переходите. Без `--ref` выбирается старший опубликованный тег `vX.Y.Z`. Для контролируемого просмотра неопубликованной ревизии можно передать точный commit или branch; в отчёте всегда показывается разрешённый commit.

Предварительный просмотр читает upstream через временный репозиторий. Он не добавляет remote, не меняет индекс, рабочие файлы и Git-настройки проекта. Применение оставляет обычный незакоммиченный diff. Настройки пользователя и личные API-ключи не переносятся из upstream.

Другой источник можно выбрать через `--source URL|path`. Относительный путь к локальной копии шаблона считается от корня целевого проекта (`KB_ROOT`), а не от временного каталога загрузки.

| Ситуация | Поведение |
|---|---|
| Файл изменился только в выпуске | Предлагается новая версия |
| Файл изменился только у вас | Ваша версия сохраняется |
| Оба изменения совпали | Путь помечается разрешённым |
| Обе стороны изменили файл по-разному | Конфликт; локальный файл сохраняется |
| Шаблон удалил неизменённый файл | Предлагается удаление |
| Новый файл конфликтует с вашим | Ваша версия сохраняется, показан конфликт |
| Ваш файл лежит внутри управляемой папки, но исключён манифестом | Он остаётся вашим |
| Рабочая копия содержит несохранённые изменения | Применение отклоняется до записи файлов |

В `package.json` сравнение идёт по объявленным JSON-полям: обновление команд оснастки не заменяет название, версию приложения и ваши дополнительные команды. Переименование обычного файла представлено удалением и добавлением с теми же проверками.

## Разобрать конфликт

Код завершения `0` означает отсутствие конфликтов, `1` — ошибку, `2` — конфликтующие пути. `--json` отдаёт структурированный отчёт.

Безопасные пути можно применить, пока конфликтные сохранены. В lock остаются старые хеши конфликтных файлов, а `pending` показывает незавершённый выпуск. Общая версия и манифест не переходят на него преждевременно.

1. Сохраните коммит безопасной части обновления.
2. Сравните свою версию конфликтного файла с исходной базой и целевым выпуском.
3. Если принимаете целевой файл, сохраните его и повторите тот же update. Совпадение будет признано разрешённым.
4. Если сохраняете проверенную комбинацию upstream и своих правок, закоммитьте её и явно подтвердите конкретный конфликт: `pnpm kb:update --ref v0.4.0 --resolve scripts/example.mjs --apply`. Содержимое остаётся вашим, а его базой становится целевая upstream-версия. Для JSON-поля используется `--resolve 'package.json#/scripts/kb:example'`. Флаг повторяется для каждого проверенного пути; несуществующий конфликт отклоняется.

Инструмент намеренно не выполняет произвольное текстовое слияние. Это сохраняет обзорность первой версии нового механизма. Автоматическое применение нескольких файлов имеет восстановление при ошибке записи; аварийное завершение процесса или системы всё равно требует проверки `git diff`.

## Старый проект без lock

Старый `kb-update` не умеет новый формат. Запустите новую версию инструмента из отдельной копии шаблона, указав каталог старого проекта через `KB_ROOT`. Перед этим сохраните свои изменения в Git.

```bash
git clone https://github.com/ha1ex/ai-kb-harness-template.git harness-upgrader
cd harness-upgrader
KB_ROOT=/absolute/path/to/project node scripts/kb-update.mjs --adopt --from ee30414
KB_ROOT=/absolute/path/to/project node scripts/kb-update.mjs --adopt --from ee30414 --apply
```

`ee30414` — известная ревизия шаблона до 0.4.0, **пример только для проекта, созданного именно с этой базы**. Укажите собственный исходный commit или тег, подтверждённый историей создания проекта. Номер `0.3.0` в старом манифесте сам по себе не доказывает конкретную ревизию. Если источник неизвестен, сначала восстановите его по истории; updater не угадывает.

Принятие базы записывает только `.harness/lock.json`, используя файлы указанной upstream-ревизии. Текущее изменённое содержимое проекта не становится baseline. Закоммитьте lock в проекте, затем запустите новую команду с `--ref v0.4.0` сначала без `--apply`.

Новые JSON-поля или области владения могут потребовать ручного разбора. Старые собственные `AGENTS.md`, `CLAUDE.md` и настройки клиента остаются на месте: добавьте общий канон и адаптер по [руководству совместимости](compatibility.md), сохранив правила проекта.

Корневой `.gitignore` также сохраняется. При миграции добавьте в него правила для локальных результатов сборки и служебных файлов: `*.tsbuildinfo`, `test-results/`, `playwright-report/`, `.remember/tasks/*.lock`, `.remember/tasks/*.lock.recovery`, `.remember/tasks/*.tmp`. Сами записи `.remember/tasks/*.json` сохраняются для продолжения работы. `.harness/lock.json` и `.harness/clients.json` коммитятся вместе с проектом: второму клону нужны исходная база и хеши управляемых копий.

## Подготовить выпуск шаблона

1. Обновить `templateVersion`, версию корневого package и CHANGELOG.
2. Убедиться, что манифест включает новые части оснастки и защищает проектные исключения.
3. Выполнить тесты и сборку.
4. Запустить `pnpm kb:release:baseline`, затем `pnpm kb:release:check`.
5. Закоммитить выпуск, создать совпадающий тег и опубликовать описание изменений.

Проверка baseline предназначена для репозитория шаблона. В созданном проекте запускаются обычные проверки harness и содержимого; исходный seed не переписывается после каждого локального изменения.
