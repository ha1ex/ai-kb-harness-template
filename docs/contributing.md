# Как улучшать шаблон

## Главное

Изменение считается готовым, когда оно работает в произвольной структуре слоёв, сохраняет существующее поведение и имеет проверяемый пример. Не переносите названия, обязательные поля или частные данные одного проекта в общее ядро.

1. Опишите поведение глазами пользователя и границы совместимости.
2. Добавьте тест, который падает без изменения.
3. Реализуйте минимальный общий контракт через `KB_ROOT` и `kb.config.mjs`.
4. Обновите документацию рядом с кодом и нейтральный пример, если он помогает проверить путь. Команды `pnpm`, пути и имена MCP-инструментов в template-owned документации сверяет `test/docs-drift.test.mjs`; новый гейт или хук добавляйте в таблицу «Слои контроля» в `docs/architecture.md`.
5. Запустите профильные тесты, затем общий набор проверок.

Проверки качества имеют разные роли. Целостность существующего реестра и переносимость путей блокируют выпуск. Читаемость по умолчанию даёт советы; строгий режим подходит для нового авторского текста. Не применяйте редакторский линтер к дословным цитатам, транскрипциям и внешнему корпусу.

Пример в `examples/human-kb/` синтетический и изолирован от настроенных индексируемых слоёв. Используйте его как эталон маршрута источник → сводка → синтез, но не как предметную схему для нового проекта.
