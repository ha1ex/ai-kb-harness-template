# Архитектура AI KB Harness

## Главное

Харнесс разделяет проектные знания, общее ядро и необязательные расширения. Проект владеет содержанием, слоями и настройками; ядро даёт поиск, проверку, агентские правила и витрину; предметные форматы подключаются отдельно. Это позволяет обновлять оснастку без навязывания чужой структуры и терминов.

| Область | Источник истины | Кто меняет |
|---|---|---|
| Содержание и решения проекта | настроенные слои базы | команда проекта |
| Структура слоёв и правила | `kb.config.mjs` | команда проекта |
| Поиск, проверки, витрина и общие правила | `scripts/`, `tools/viewer/`, `harness/` | авторы шаблона |
| Локальная рабочая память | `.context/`, `.remember/` | пользователь и агент |
| Предметные форматы | отдельные расширения | владелец расширения |

## Поток знания

```text
сырой материал → сводка источника → wiki / синтез → решение → результат
       │                 │                │             │
       └─────────────────┴──── ссылки ────┴─────────────┘
                              ↓
                    индекс → поиск → ответ → проверка
```

Порядок слоёв задаёт `layers.indexable`, а их смысл определяет проект. Проверка происхождения использует `layers.rank` и `provenance` из конфигурации. Инструменты разрешают корень через `KB_ROOT`, поэтому одна установка может обслуживать несколько баз.

Markdown остаётся переносимым первичным форматом. Индекс и витрина являются представлениями: их можно пересобрать из файлов. Поддерживаемая разметка описана в [диалекте Markdown](./markdown-dialect.md), а читательский путь — в [человеческом интерфейсе](./human-interface.md).

## Контуры харнесса

- **Контекст:** краткие правила и нужные проекту документы загружаются по задаче.
- **Память:** подтверждённые решения и состояние работы хранятся в файлах, а не только в истории чата.
- **Поиск:** локальный индекс объединяет лексический и семантический поиск; выбранная LLM подключается отдельно.
- **Контроль:** ссылки, происхождение, метаданные и структура проверяются механически там, где это возможно.
- **Оценка:** повторяемые сценарии измеряют качество поиска и рабочих процедур.
- **Наблюдение:** локальный журнал помогает увидеть пустые выдачи и повторяющиеся ошибки без хранения полного текста запросов.
- **Улучшение:** результаты проверок и прогонов становятся входом для следующего изменения правил или навыка.

Такое устройство следует распространённому подходу «контекст и память как файлы, возможности как отдельные модули». Похожую модель документирует [LangChain Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview). Межклиентская поверхность инструментов использует открытый [Model Context Protocol](https://modelcontextprotocol.io/docs/learn/architecture). Эти источники объясняют архитектурные ориентиры; конкретные гарантии определяются кодом и тестами этого репозитория.

## Владение и обновление

Манифест шаблона отделяет управляемые файлы от файлов проекта. Исключение проекта имеет приоритет над управляемой родительской папкой. Обновление сравнивает установленную базу с новой версией и останавливается при конфликте с пользовательской правкой.

Сгенерированные адаптеры и навыки имеют отдельный жизненный цикл. Проверка сообщает расхождение, а настройка записывает только явно выбранные клиенты. Наличие общей папки навыков само по себе не доказывает, что конкретный клиент её загрузил.

## Границы гарантий

Проверка существования ссылки подтверждает путь, но не истинность утверждения. Подпись эффекта решения (`approved_hash`) защищает от случайной правки после одобрения и фиксирует основание, но не от агента, который сам посчитает хеш: личность она не удостоверяет. Семантическое совпадение даёт сигнал для ревью, а не доказательство. `audience` управляет навигацией и не ограничивает доступ. Локальный поиск не означает, что подключённая LLM работает локально.

Специализированные редакторы P&L, оргструктуры, процессов и дорожных карт не входят в универсальное ядро. Их возможные контракты перечислены в [каталоге расширений](./extensions.md).

## Слои контроля

Три слоя, как и в любой системе «агент предлагает, код проверяет, человек одобряет»: детерминированный код-гейт блокирует, advisory-проверка советует, подтверждение человека — отдельная запись. Умолчание для содержания базы — «к человеку»: предложение становится решением только после записи подтверждения. Изменили гейт или хук — обновите эту таблицу в том же изменении; тест `test/docs-drift.test.mjs` сверяет её с `scripts/git-hooks/check.mjs`, хуками `.claude/settings.json` и CI.

| `scripts/check-harness.mjs` — контракты ролей, сценариев, профиль, копии навыков у клиентов | код-гейт + advisory (`warnings`) | ошибка конфигурации — exit 1; навыки без потребителя — предупреждение | pre-push, CI (`pnpm check`), вручную | да |

| `scripts/kb-profile.mjs apply --by --note` | подтверждение человека | профиль остаётся черновиком | вручную | да |

| `scripts/kb-research.mjs` — reviewer на frontier-тире, лимиты | код-гейт по политике + независимое ревью | задача не завершается | вручную или `--execute` | да |
| `scripts/check-documents.mjs` — каталог, методологии и свежесть HTML/PDF | код-гейт | ошибка сборки или проверки | вручную, общий pre-push и CI | да |

Записи подтверждения фиксируют факт согласования локально и не удостоверяют личность. Разрешения и хуки Claude Code — ранняя обратная связь для одного клиента, не гарантия для других: общий гейт — `pnpm check` и CI (см. [совместимость](./compatibility.md)).

`kb-doctor` входит также в общий `pnpm check`. Проверку возраста могут пропускать только точные пути, явно указанные владельцем в `doctor.excludePaths`. Остальные проверки документа сохраняются.

## Рабочая система проекта

Контракты ролей и сценарии в `harness/` задают входы, артефакты, проверки и порядок этапов. Необязательный профиль в `00_context/work-system.json` выбирает рекомендуемые роли и процедуры, добавляет проектные специализации. Профиль и очередь находок в `.remember/` принадлежат проекту и сохраняются при обновлении ядра.

Контекст задачи собирается из правил, контрактов, выбранных процедур, источников и принятых уроков. Полный документ либо помещается в бюджет, либо явно остаётся для чтения; отсутствие обязательного материала препятствует готовности пакета. Состояние этапов хранится в существующей записи задачи. Хеши артефактов выявляют изменение после проверки.

Общий реестр скиллов используется адаптерами клиентов и SkillOpt. Кандидат проходит сравнение на одинаковых примерах; запись подтверждения относится к конкретным хешам. Эти записи фиксируют подтверждение в локальном процессе и не удостоверяют личность человека. Роли также не изолируют инструменты процесса.
