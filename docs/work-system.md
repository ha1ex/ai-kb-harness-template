# Рабочая система проекта

## Главное

Рабочая система подбирает контекст по роли и этапу, сохраняет проверяемые результаты и помогает продолжить задачу в другом агенте.

- Роль определяет ответственность; сценарий — порядок этапов и обязательные результаты.
- Навык описывает процедуру; профиль выбирает подходящие проекту роли, сценарии и навыки.
- Очередь замечаний хранит проблемы знаний и подтверждённый опыт работы раздельно.

Начните с `pnpm kb:context --task research-01 --workflow research --json`. Профиль необязателен. Команды контекста, профиля и очереди не вызывают модель. Внешняя база через `KB_ROOT` без новых контрактов сохраняет прежний контекст; выбор сценариев требует установки контрактов в эту базу.

## Выбрать работу

| Сценарий | Когда использовать | Этапы по порядку |
|---|---|---|
| `ingest` | Появился новый источник | `preserve` → `summarize` → `impact` → `update` → `review` |
| `research` | Нужно ответить на вопрос | `scope` → `gather` → `synthesize` → `review` → `save` |
| `decision` | Нужно подготовить решение | `options` → `review` → `propose` → `record` |
| `revalidate` | Изменились основания вывода | `changes` → `impact` → `revise` → `review` |

Контракты находятся в [`harness/workflows/`](../harness/workflows/), роли — в [каталоге ролей](../harness/roles/README.md). Один агент может последовательно исследовать, редактировать и координировать. Независимая проверка требует отдельного контекста; средства запуска агентов выбирает клиент.

## Настроить профиль проекта

После [обычной установки](../README.md#начать-проект) агент читает цель, материалы `00_context/`, открытые вопросы и типичные задачи. На этой основе он готовит небольшое предложение. Дополнительные роли нужны только там, где обычных недостаточно.

Пример проекта, который регулярно отвечает на исследовательские вопросы и перепроверяет выводы:

```bash
mkdir -p .context/work-system
cat > .context/work-system/profile.json <<'JSON'
{
  "version": 1,
  "status": "draft",
  "purpose": "Отвечать на исследовательские вопросы с проверяемыми источниками",
  "roles": ["coordinator", "researcher", "editor", "reviewer", "librarian"],
  "workflows": ["research", "revalidate"],
  "skills": ["skill-ingest", "skill-decision-log"],
  "customRoles": {},
  "customWorkflows": {}
}
JSON
pnpm kb:profile propose --file .context/work-system/profile.json
pnpm kb:profile show --json
```

Человек проверяет назначение и предложенный состав. После подтверждения точного предложения выполните команду, подставив имя и ссылку на согласование:

```bash
pnpm kb:profile apply --by <human> --note <authorization-reference>
pnpm harness:check
pnpm kb:context --task research-01 --workflow research --json
```

`propose` сохраняет предложение в `.context/work-system/proposal.json`; `apply` проверяет его и исходную версию, записывает активный профиль в `00_context/work-system.json` и основание согласования. Если предложение или действующий профиль изменились, подготовьте и согласуйте новую версию. Черновик не включает проектные расширения.

`roles` и `workflows` показывают рекомендуемый состав; базовые сценарии остаются доступны явно. `skills` добавляет процедуры в контекст активного профиля. `customRoles` и `customWorkflows` содержат контракты того же формата, что JSON-файлы шаблона. Собственные ID должны отличаться от базовых. Обязательный контекст собственной роли должен существовать. Профиль не меняет разрешения клиента; имя в записи согласования не подтверждает личность.

Инструкцию собственной роли храните в project-owned неиндексируемом файле, например `.remember/roles/<id>.md`, и укажите его в `customRoles.<id>.requiredContext`. Это инструкции, а не доказательства: ссылки `[source:]` на такие файлы недопустимы. Новые процедуры для роли создавайте из эталона командой `pnpm skill new <name>` и подключайте через `skills` профиля или этап сценария.

## Читать пакет контекста

```bash
pnpm kb:context --task research-01 --workflow research --max-chars 24000 --json
pnpm kb:context --task research-01 --role reviewer --json
```

В JSON поле `work` содержит:

| Поле | Что делать |
|---|---|
| `role`, `stage`, `skills` | Прочитать ответственность, текущий этап и назначенные процедуры |
| `documents` | Прочитать включённые документы; они передаются целиком |
| `missing` | Восстановить обязательный документ или исправить ссылку |
| `deferred` | Открыть документ отдельно либо увеличить `--max-chars` |
| `staleArtifacts` | Перепроверить изменённые результаты завершённых этапов |
| `lessons` | Учесть принятый опыт для выбранных роли, сценария, навыка и задачи |
| `ready` | Проверить готовность пакета к работе; это не оценка качества ответа |

Лимит `--max-chars` ограничивает текст документов, уроков и контрактов внутри `work`; служебные поля JSON, состояние Git и задачи добавляют объём. Большой профиль передаётся кратко, а полный файл попадает в `deferred`. Непоместившийся обязательный документ или устаревший результат даёт `ready: false`. Внешние источники требуют отдельного чтения: команда не загружает их из сети.

## Пример: исследование по этапам

Пример начинает настоящую задачу и оставляет содержательную работу агенту. Он не создаёт фиктивных доказательств или пройденного ревью. Команды выполняются из корня проекта; используйте свободный ID задачи и свой `owner`.

**1. Определите вопрос.** Получите контекст, запишите краткое задание и начальную передачу:

```bash
pnpm kb:context --task research-01 --workflow research --json
mkdir -p .context/research-01
cat > .context/research-01/brief.md <<'MARKDOWN'
# Главная неопределённость проекта

Вопрос: какое доказательство нужно получить следующим?
Критерии: ответ опирается на источники; пробелы названы явно;
выбран следующий шаг; независимый рецензент проверил основания.
MARKDOWN
cat > .context/research-01/handoff.json <<'JSON'
{
  "goal": "Определить главное недостающее доказательство и следующий шаг",
  "acceptanceCriteria": ["Ответ имеет источники, явные пробелы и независимое ревью"],
  "decisions": [],
  "workflow": "research",
  "status": "active",
  "sources": [],
  "checks": [],
  "openQuestions": [],
  "nextStep": "Собрать доказательства для ответа",
  "stages": [{
    "id": "scope",
    "status": "complete",
    "result": "Вопрос и критерии записаны в задании",
    "artifacts": [{"name": "brief", "path": ".context/research-01/brief.md"}]
  }]
}
JSON
pnpm kb:session save --task research-01 --owner author-01 --file .context/research-01/handoff.json
pnpm kb:context --task research-01 --json
```

Теперь `work.stage.id` — `gather`. `kb:context` сам не сохраняет этап; это делает `kb:session save`.

**2. Соберите доказательства и подготовьте ответ.** Ищите материалы через `pnpm kb:search "главный вопрос проекта"`, читайте саммари и необходимые оригиналы. Для каждого следующего этапа сначала создайте содержательный файл, затем обновите передачу и выполните те же две команды `save` и `context`.

| Этап | Обязательное имя файла в `artifacts` | Пример пути | Содержимое |
|---|---|---|---|
| `gather` | `findings` | `.context/research-01/findings.md` | Утверждения со ссылками, противоречия, пробелы |
| `synthesize` | `answer` | `.context/research-01/answer.md` | Ответ, его основания и следующий шаг |
| `review` | `review` | `.context/research-01/review.md` | Независимая проверка критериев и смысла источников |
| `save` | `result` | `.context/research-01/result.md` | Итог работы и ссылки на сохранённые материалы |

Пример записи после реально выполненного `gather`: добавьте её в `stages`, заполните `sources` путями прочитанных источников и обновите `nextStep`.

```json
{
  "id": "gather",
  "status": "complete",
  "result": "Доказательства, противоречия и пробелы записаны",
  "artifacts": [{"name": "findings", "path": ".context/research-01/findings.md"}]
}
```

`stages` объединяется с сохранёнными этапами по `id`; пропущенный этап сохраняет прежнее состояние. Для `synthesize` используйте тот же формат с именем `answer`. Завершить этап без непустого файла или раньше предыдущего не получится.

**3. Проведите независимое ревью.** В другом контексте откройте `pnpm kb:context --task research-01 --role reviewer --json`. Передайте рецензенту задание, ответ, исходные доказательства и критерии. Он сохраняет отчёт; автор задачи записывает его результат. Если замечания требуют исправления ответа, сначала переоткройте затронутые этапы.

Если нужны исправления, сохраните этап как `active`, а `review.status` как `changes-requested`; приложите фактический отчёт и идентификаторы контекстов. После реальной успешной проверки добавьте этап со своими идентификаторами:

```json
{
  "id": "review",
  "status": "complete",
  "result": "Рецензент проверил критерии и основания; итог в отчёте",
  "artifacts": [{"name": "review", "path": ".context/research-01/review.md"}],
  "review": {
    "mode": "independent",
    "status": "passed",
    "reviewer": "reviewer-02",
    "contextId": "review-session-02",
    "authorContextId": "author-session-01"
  }
}
```

Разные строки ID — лишь формальный минимум. Они не доказывают, что проверку действительно выполнил другой контекст. Если отдельный контекст недоступен, сохраните незавершённый этап и следующий шаг.

**4. Сохраните результат и завершите задачу.** После сохранения ревью соберите итоговый файл, добавьте этап `save` с именем `result` и сохраните его. Устойчивые знания разместите в соответствующем слое базы по [правилам доказательств](../harness/rules/evidence.md); временные файлы остаются в `.context/`.

```bash
pnpm harness:check
pnpm kb:verify --scan --provenance --no-semantic
```

Занесите фактические команды и результаты в `checks`: `command`, `outcome`, `evidence`. Когда все критерии выполнены, все этапы завершены, проверки пройдены и открытых вопросов нет, задайте в передаче `status: complete`, непустые `result` и `nextStep`, затем выполните:

```bash
pnpm kb:session save --task research-01 --owner author-01 --file .context/research-01/handoff.json
pnpm kb:context --task research-01 --json
```

В сохранённой задаче `status` будет `complete`, а `work.stage` — `null`. Для сценария `decision` этап `record` дополнительно требует `approval: {"by": "<human>", "reference": "<authorization-reference>"}`. До согласования материал остаётся предложением.

## Изменения и продолжение

Контрольные отпечатки привязаны к содержимому файлов и применённым контрактам роли, сценария и навыков. Если после ревью изменился `answer.md`, пакет покажет устаревший результат. В передаче установите `status: active` и явно переоткройте этапы:

```json
{
  "stages": [
    {"id": "synthesize", "status": "pending", "result": "", "artifacts": []},
    {"id": "review", "status": "pending", "result": "", "artifacts": []},
    {"id": "save", "status": "pending", "result": "", "artifacts": []}
  ]
}
```

Сохраните передачу обычной командой и пройдите эти этапы заново. Старое ревью и согласование не подтверждают изменённый результат. Смена сценария требует новой задачи. Хеши выявляют изменение сохранённых файлов; истинность источника и появление новых внешних данных проверяются отдельно.

Другой автор продолжает ту же задачу после явной передачи записи:

```bash
pnpm kb:session transfer --task research-01 --owner author-01 --to author-02
pnpm kb:context --task research-01 --json
```

## Замечания и опыт

```bash
pnpm kb:doctor
pnpm kb:findings list --json
pnpm kb:findings scan --json
pnpm kb:digest
```

Doctor по умолчанию только читает. `scan` запускает локальные проверки doctor и явно сохраняет наблюдения; эквивалент — `pnpm kb:doctor --record-findings --json`. Поиск проблем использует файлы и доступный локальный индекс, без модели, сети и оценки смысла текста. Digest показывает очередь и предлагаемые действия.

Собственную находку добавляйте через `pnpm kb:findings add --file <finding.json>`. Пример формы; содержание и ссылки замените реальным наблюдением:

```json
{
  "kind": "feedback",
  "title": "При саммари теряется дата источника",
  "problem": "Без даты читатель не может оценить актуальность основания",
  "paths": ["skills/skill-ingest.md"],
  "evidence": [{
    "source": ".context/research-01/review.md",
    "observation": "В ревью указан пропуск даты в саммари"
  }],
  "suggestedAction": "Проверить на примерах требование сохранять дату источника",
  "role": "researcher",
  "workflow": "ingest",
  "skill": "harness-evidence"
}
```

`knowledge` описывает предметную проблему: устаревший вывод, потерянную ссылку, конфликт источников. `feedback` описывает опыт работы. Записи хранятся в `.remember/findings/`; новые наблюдения имеют статус `open`. Повторный scan сохраняет историю и ранее принятый статус.

После подтверждения человеком полезного урока:

```bash
pnpm kb:findings transition --id <id> --status accepted --by <human> --note <confirmation>
pnpm kb:context --task ingest-01 --workflow ingest --role researcher --json
```

Только `feedback` со статусом `accepted` попадает в `work.lessons` при совпадении всех указанных ограничений: `role`, `workflow`, `skill`, `task`. Неуказанное поле не ограничивает применение урока. `resolved` отмечает устранённую проблему, `dismissed` — отклонённую; `open` возвращает её к разбору. Переход хранит автора и основание, но не проверяет личность. Принятый урок не редактирует навыки автоматически: изменение проходит [предложение, сравнение, согласование и применение](../skills/README.md#проверяемое-изменение).

`pnpm kb:dream` готовит запрос для агента; готовый запрос не является аудитом. Вызов модели требует `--execute` и настроенного провайдера. Даже выполненный отчёт содержит предложения, которые нужно проверить. `pnpm kb:metrics` оставляет показатели неизвестными при недостатке наблюдений. `firstPassCompletion` измеряет независимое ревью с первой попытки по задаче и этапу; он не означает приёмку всей задачи человеком.

## Реестр ролей, сценариев и навыков

`pnpm kb:roster` (или `--json`) показывает роли, этапы сценариев, навыки и их потребителей: какие роли и этапы ссылаются на навык, входит ли он в активный профиль, сколько у него проверок и копий у клиентов. Навык без роли, этапа или активного профиля отмечен как не подключённый: в пакет `kb:context` он не попадает, клиент может загрузить его только по `description`. При активном профиле `pnpm harness:check` печатает предупреждение о таких навыках; код выхода не меняется. Команда только читает файлы и не вызывает модель.

## Пределы проверки

CLI проверяет контракты, файлы, порядок этапов и записи согласований. Человек и агент проверяют смысл источников, качество вывода и достижение цели. Прохождение локальных проверок не подтверждает живые сессии всех моделей или клиентов; их состояние отражает [матрица совместимости](compatibility.md).
