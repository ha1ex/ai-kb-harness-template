# Процедуры проекта

Навык описывает повторяемую работу: когда его использовать, что прочитать, какой результат получить и как его проверить. Агент открывает `SKILL.md` через свой клиент или пакет `kb:context`; автоматическое распознавание триггеров зависит от клиента.

## Где хранить

| Каталог | Назначение |
|---|---|
| [`harness/skills/`](../harness/skills/) | Переносимые процедуры шаблона; обновляются вместе с ним |
| `skills/<name>/SKILL.md` | Собственные процедуры проекта; рядом можно хранить примеры, проверки и справочные файлы |
| `skills/<name>.md` | Поддерживаемый прежний формат проектного навыка |

Имя должно быть уникальным во всех каталогах. Не храните одновременно плоский файл и `SKILL.md` одного навыка; каталог с проверками рядом с прежним плоским файлом допустим. Не используйте символические ссылки. Материалы внешних библиотек в `06_outputs/` служат источниками; их наличие не устанавливает навык агенту.

## Формат

```markdown
---
name: project-source-summary
description: Подготовить саммари нового источника по правилам проекта.
---

# Саммари источника

Прочитайте harness/rules/evidence.md. Сохраните оригинал, выделите
подтверждённые утверждения и пробелы, добавьте ссылки и проверьте результат.
```

`name` совпадает с именем каталога или плоского файла, `description` — непустая строка. Для новых процедур используйте каталог с `SKILL.md`. Старые поля `triggers`, `inputs`, `outputs` могут оставаться в проектных файлах, но сами по себе не запускают инструменты.

Существующие процедуры: [приём источника](skill-ingest.md), [журнал решений](skill-decision-log.md). Общие справочные процедуры: [профиль проекта](../harness/skills/harness-project-profile/SKILL.md), [работа по этапам](../harness/skills/harness-workflow/SKILL.md), [поддержка знаний и процедур](../harness/skills/harness-maintain/SKILL.md).

## Новый навык

Начинайте с эталона, а не с соседнего навыка: `pnpm skill new <name>` копирует `harness/templates/skill/` в `.context/skills/<name>/`, подставляет имя и печатает следующий шаг. В `skills/` черновик попадает только через `propose → compare → approve → apply`. Навык, не назначенный роли, этапу сценария или активному профилю, в пакет `kb:context` не попадает; клиент может загрузить его только по `description`.

Необязательные поля frontmatter `status: draft | verified | deprecated` и `version: <целое>` читают `pnpm skill list` и `kb:context`. `verified` ставит человек коммитом после пройденного сравнения; `deprecated` делает навык недостижимым для ролей, этапов и профиля и убирает его копии у клиентов при `pnpm harness:setup`. Неизвестное значение статуса — ошибка обнаружения.

## Проверяемое изменение

Подготовьте предложенный `SKILL.md`, объяснение проблемы и проверочные случаи. Команды SkillOpt работают с проектными навыками; изменение процедуры шаблона требует обычного изменения шаблона.

```bash
pnpm skill propose project-source-summary --file .context/source-summary/SKILL.md --reason "Сохранять противоречия между версиями источника" --evals .context/source-summary/evals
pnpm skill compare <run>
pnpm skill compare <run> --execute
pnpm skill diff <run>
```

`propose` возвращает ID запуска и сохраняет предложение в `.context/skillopt/<run>/`. Для нового навыка обязателен `--evals`; для существующего можно использовать проверки рядом с ним. Пример формата — [проверочный случай приёма источника](skill-ingest/evals/happy-path.yaml).

`compare` без `--execute` готовит запросы и не вызывает модель. С `--execute` нужен настроенный провайдер; текущий и предложенный варианты проходят одни и те же случаи. Подготовка запросов не считается пройденным сравнением. В `comparison.json` сохраняются результаты, основания оценки и отпечатки входов.

После просмотра разницы, результатов проверки и подтверждения конкретного предложения человеком:

```bash
pnpm skill approve <run> --by <human> --note <authorization-reference>
pnpm skill apply <run>
pnpm harness:setup
pnpm harness:check
```

Без выполненного успешного сравнения и подтверждения применение отклоняется. Изменение текущего навыка, предложения или случаев делает прежнюю проверку устаревшей. Целевой навык должен быть без несохранённых в Git изменений. `apply` сохраняет резервную копию, записывает файлы и добавляет их в индекс Git; перед коммитом проверьте разницу. Согласование фиксируется локально и не проверяет личность. Существующие команды `reflect`, `diff`, `rollout` остаются доступны; точные параметры показывает `pnpm skill --help`.

После применения или отката `harness:setup` обновляет копии навыков у уже выбранных клиентов. Локально изменённые копии сохраняются и требуют разбора конфликта. Без синхронизации клиент может продолжать читать прежнюю процедуру.

Связь навыков с ролями, профилем и уроками описана в [рабочей системе](../docs/work-system.md).
